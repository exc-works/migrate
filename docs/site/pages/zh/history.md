# 历史与基线

迁移历史表记录版本、文件名与哈希。判断已经执行了哪些变更时，需要同时检查历史和实际数据库结构。

## 查看状态

```sh
migrate status
migrate status --output json
```

表格输出 Version、Filename、Hash 和 Status；自动化流程可以读取 JSON。

| 状态 | 含义 | 后续操作 |
| --- | --- | --- |
| `pending` | 文件尚未应用 | 检查后运行 `up` |
| `applied` | 版本已成功应用 | 保持文件不变 |
| `baseline` | 已登记历史，但没有执行文件 | 保留接管时的历史 |
| `outOfOrder` | 待执行版本低于已应用版本 | 检查乱序策略 |
| `hashMismatch` | 当前文件与记录的哈希不同 | 恢复历史文件 |
| `filenameMismatch` | 当前文件名与记录不同 | 恢复历史文件名 |

哈希或文件名不一致会阻断执行。不要修改已应用迁移来完成新的结构变更，应新增更高版本。
脚本校验和只覆盖入口源码，不包含导入的 helper，见[模块可复现性](./modules#checksums)。

## 为已有数据库建立基线 {#baseline}

仅当数据库已与要接管的迁移文件一致时，才使用基线。它只登记历史，不执行 SQL 或脚本。

1. 对比现有结构、数据与迁移文件。
2. 如有需要，先通过 `migrate create` 创建历史表。
3. 执行 `migrate baseline`，再通过 `migrate status` 检查。
4. 后续变更新增更高版本，按正常流程执行。

基线不能修复执行到一半的迁移。应先确定数据库实际状态；盲目登记历史可能掩盖尚未完成的变更。
